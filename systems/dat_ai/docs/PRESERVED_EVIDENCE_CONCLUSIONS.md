**Status**: LOCKED. These four conclusions were reached through empirical
verification during Phase C (disposable PostGIS testing, direct code
reading, regression tests) and are recorded here as canonical fact so
future missions build on them rather than re-litigate them. Each links to

## 1. Migration 001

**Status**: `RETIRED_FROM_ACTIVE_CHAIN` / `PRESERVED_AS_HISTORICAL_PROVENANCE`

Migration 001 (`backend/migrations/001_satellite_tables.sql` in the donor)
predates the SQLAlchemy ORM models and is fully superseded by
`Base.metadata.create_all()`. It additionally references a
`valuation_history` table that does not exist anywhere in the current
schema, so no idempotency fix would make it safe to run. It is preserved,
unmodified, at `migrations/retired/001_satellite_tables.sql.retired` with
`migrations/retired/RETIREMENT_NOTE.md` explaining why. **It must never be
added back to the active migration chain** (`002` → `003` → `004` → `005`).

Evidence: `DATAI_PHASE_AB_VERIFICATION_REPORT.md` §2, `DATAI_DEFECT_REPAIR_EVIDENCE.md`.

## 2. Migration 003, section 9 (legacy `properties` labelling)

**Status**: `ACTIVE_HISTORICAL_HONESTY_MECHANISM`

This section labels pre-existing synthetic `properties` rows (generated by
`worker/tasks.py` via `random.uniform()`) as `data_class='synthetic'`, and
must continue to do so on any deployment where that legacy table exists.
It is **not** dead code. It is guarded with
`IF to_regclass('public.properties') IS NOT NULL THEN ... END IF` so it
safely no-ops on a fresh canonical deployment (where `properties` never
existed) while still performing its honesty function on any deployment
that inherited the legacy table. **Do not remove this guard's underlying
logic** — only the existence check may ever be revisited, and only with
evidence that no deployment anywhere still has the legacy table.

Confirmed distinct from `routes/tiles.py`'s use of the string `'properties'`,
which is only an MVT vector-tile layer-name label passed to `ST_AsMVT`, not
a table reference — the route queries `FROM listings`.

Evidence: `DATAI_DEFECT_REPAIR_EVIDENCE.md` (Defect 2 section), `migrations/003_satellite_provenance.sql` inline comments.

## 3. `bytes_downloaded` (and `retry_count`, same class)

**Root cause, locked**: SQLAlchemy `Column(..., default=0)` sets a
**client-side (Python/ORM) default only** — it never appears in the
generated DDL. A raw SQL `INSERT` bypassing the ORM therefore violates
`NOT NULL` with no fallback. This is an ORM-default vs. server-side-DEFAULT
semantics gap, not a logic bug in the ingestion code.

**Fix, locked**: `server_default=text("0")` on the SQLAlchemy column
(`app/models/satellite.py`) **plus** an explicit
`ALTER COLUMN ... SET DEFAULT 0` in `migrations/003_satellite_provenance.sql`
(needed because `ADD COLUMN IF NOT EXISTS ... DEFAULT 0` is a no-op once
the ORM has already created the column without a server default — the two
bootstrap paths were fighting each other).

**Regression coverage requirement, locked**: both the raw-SQL insertion
path AND the ORM insertion path must be covered by tests, permanently —
this defect was invisible to ORM-only testing and only surfaced via a raw
SQL insert. `tests/integration/test_defect_regressions.py::TestDefect1BytesDownloadedServerDefault`
covers the raw-SQL path (`test_raw_sql_insert_without_bytes_downloaded_succeeds`,
`test_explicit_nonzero_value_still_respected`) and must not be reduced to
ORM-only coverage in any future revision.

Evidence: `DATAI_DEFECT_REPAIR_EVIDENCE.md` (Defect 1 section).

## 4. Valuation implementations

**Status**: `RULE_BASED` / `UNTESTED` / `PARTIAL` / `DONOR_ONLY`

`source/valuation_engine.py` and `source/valuation_algorithm.py` contain
genuine, non-fabricated comparable-sales scoring logic (no `random`/`mock`/
`placeholder` markers found). They are **not fabricated** and **not
ported**: zero test coverage for either file, two competing implementations
never reconciled, hardcoded `/tmp/` I/O paths, dict-based rather than
ORM-integrated.

**Binding constraint, locked**: DAT.AI must not expose valuation as an
operational capability in Phase C or represent it as more mature than
`DONOR_ONLY` in any institutional report, health check, or documentation.
The institutional contract's capability-status model (see
`DATAI_INSTITUTIONAL_CONTRACT.md`) reports valuation as `NOT_COMMISSIONED`
specifically to make this unambiguous in every report, not just in prose
documentation that could be overlooked.

Evidence: `DATAI_PHASE_C_RECOVERY_REPORT.md` (valuation assessment), `DATAI_PHASE_D_ENTRY_CRITERIA.md`.
