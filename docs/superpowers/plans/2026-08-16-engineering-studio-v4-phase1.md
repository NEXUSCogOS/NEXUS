## Task 1: Evidence Ledger

Create `systems/engineering_studio/studio_v3/observatory/evidence_ledger.py`.

Implement `EvidenceLedger`, an append-only, hash-chained SQLite-backed event
log.

Database file: `systems/engineering_studio/studio_v3/observatory/evidence.db`
(created on first use if absent; do not commit the `.db` file itself — add
`*.db` under this directory to `.gitignore` if not already ignored).

Schema (table `events`):
- `event_id` TEXT PRIMARY KEY (a UUID4 hex string, generated by the ledger)
- `timestamp` TEXT NOT NULL (UTC ISO-8601, e.g. `datetime.now(timezone.utc).isoformat()`)
- `agent` TEXT NOT NULL
- `action` TEXT NOT NULL
- `input_data` TEXT (JSON-encoded, nullable)
- `output_data` TEXT (JSON-encoded, nullable)
- `test_result` TEXT (JSON-encoded, nullable — e.g. `{"passed": true, "count": 5}`)
- `resource_cost` TEXT (JSON-encoded, nullable — shape defined by Task 2, but
  this table just stores whatever dict it's given)
- `files_modified` TEXT (JSON-encoded list of paths, nullable)
- `git_commit_hash` TEXT (nullable)
- `verification_status` TEXT NOT NULL DEFAULT 'unverified'
  (one of: 'unverified', 'verified', 'refuted' — Task 3's Auditor writes this)
- `prev_hash` TEXT NOT NULL (hash of the previous record; `'0'*64` for the first record)
- `record_hash` TEXT NOT NULL (SHA-256 of this record's canonical JSON
  representation, INCLUDING `prev_hash`, EXCLUDING `record_hash` itself)

Public API on `EvidenceLedger`:
- `__init__(self, db_path: str | Path)` — opens/creates the DB, creates the
  table if absent, ensures a `WAL` journal mode for concurrent-safe appends.
- `record_event(self, agent: str, action: str, *, input_data=None,
  output_data=None, test_result=None, resource_cost=None,
  files_modified=None, git_commit_hash=None) -> str` — inserts a new event,
  computes `prev_hash` from the current last record (or genesis value),
  computes `record_hash`, returns the new `event_id`. Canonical JSON for
  hashing: `json.dumps(record_dict, sort_keys=True, separators=(',', ':'))`
  where `record_dict` is every column above except `record_hash` itself.
- `verify_chain(self) -> tuple[bool, str | None]` — walks every record in
  timestamp order, recomputes each `record_hash` from its stored fields and
  checks it matches, and checks each record's `prev_hash` matches the
  previous record's `record_hash`. Returns `(True, None)` if the whole chain
  is intact, or `(False, event_id)` naming the first record that fails
  either check.
- `get_event(self, event_id: str) -> dict | None`
- `query_events(self, *, agent: str | None = None, action: str | None = None,
  since: str | None = None) -> list[dict]` — simple filtered query, AND
  semantics across provided filters, `since` compares against `timestamp`
  lexically (ISO-8601 sorts correctly as strings).
- `set_verification_status(self, event_id: str, status: str) -> None` —
  updates `verification_status` for an existing event. This does NOT change
  `record_hash` (the hash covers only the original recorded facts, not the
  auditor's later verdict — verification_status is deliberately mutable
  metadata layered on top of the immutable record).

Write tests in
`systems/engineering_studio/studio_v3/tests/test_evidence_ledger.py`:
- Recording an event returns a UUID-shaped `event_id` and the event is
  retrievable via `get_event`.
- Recording 3 events produces a valid chain (`verify_chain()` returns
  `(True, None)`).
- Tampering with a stored record's `output_data` directly via raw SQL
  (`UPDATE events SET output_data = ... WHERE event_id = ...`), then calling
  `verify_chain()`, must detect it: returns `(False, <that event_id>)`.
- `query_events` filters correctly by `agent` and by `action`.
- `set_verification_status` updates the field without altering `record_hash`
  (assert `record_hash` unchanged before/after).

Report file: docs/superpowers/plans/.sdd-workspace/2026-08-16-engineering-studio-v4-phase1/task-1-report.md
(the sdd-workspace script will give you the exact path — use that path, this

## Task 2: Resource Economics Engine

Depends on: Task 1 (imports `EvidenceLedger` to optionally log measurements,
but must also work standalone).

Create `systems/engineering_studio/studio_v3/observatory/resource_economics.py`.

Implement `ResourceMeter`, a context-manager class that measures real
resource consumption for a block of work.

```python
with ResourceMeter(label="some_operation") as meter:
    ... do work ...
result = meter.result  # populated after __exit__
```

`meter.result` is a dict with these REAL, measured (not estimated) fields:
- `label`: str, as passed in
- `wall_seconds`: float — `time.perf_counter()` delta
- `cpu_seconds`: float — `time.process_time()` delta (this process's CPU time,
  not wall clock — they differ under I/O wait or multiprocessing)
- `peak_rss_kb`: int — `resource.getrusage(resource.RUSAGE_SELF).ru_maxrss`
  read at exit (on macOS this is already in bytes per the platform's libc,
  NOT kb as the Linux docs claim — detect via `sys.platform == 'darwin'` and
  divide by 1024 to normalize to KB consistently across platforms; write a
  comment explaining this, it is a real, well-known cross-platform gotcha,
  don't silently get it wrong)
- `start_timestamp` / `end_timestamp`: UTC ISO-8601 strings

Also implement `measure_storage_delta(path: str | Path) -> dict` (standalone
function, not part of the context manager): takes a directory or file path,
returns `{"path": str, "size_bytes": int, "measured_at": <iso8601 utc>}`
using `os.stat` for a file or a real recursive walk-and-sum
(`os.walk` + `os.path.getsize`) for a directory. This is for taking
before/after snapshots — call it twice around an operation and diff the
`size_bytes` yourself; the function itself does not diff.

Also implement `measure_directive_backlog(directives_root: str | Path) -> dict`:
given the real `.directives-ingestion` directory structure (subdirs
`pending/`, `approved/`, `in-progress/`, `completed/`, `rejected/`), returns
counts and total bytes per subdir, using real `os.scandir` / `os.stat` calls
— this is meant to replace hand-run one-off analysis scripts (like the ones
written earlier this session) with a reusable, testable function.

Write tests in
`systems/engineering_studio/studio_v3/tests/test_resource_economics.py`:
- `ResourceMeter` around a `time.sleep(0.05)` block reports `wall_seconds`
  >= 0.05 (allow slack, assert `> 0.04`).
- `ResourceMeter` around a CPU-bound loop (e.g. sum of range(10_000_000))
  reports `cpu_seconds > 0`.
- `measure_storage_delta` on a temp file of known size (write N bytes,
  measure, assert `size_bytes == N`).
- `measure_storage_delta` on a temp directory with 2 known-size files sums
  correctly.
- `measure_directive_backlog` on a temp directory structured like
  `.directives-ingestion` (create the 5 subdirs, drop known files in some of
  them) returns correct counts per subdir.

Do NOT run `measure_directive_backlog` against the real
`.directives-ingestion` (67k+ files) inside a unit test — that belongs in a
separate manual/integration script, not the fast unit suite. Use a temp dir
fixture.

## Task 3: Independent Auditor

Depends on: Task 1 (EvidenceLedger), Task 2 (ResourceMeter, for optional
self-measurement of audit runs).

Create `systems/engineering_studio/studio_v3/observatory/independent_auditor.py`.

Implement `IndependentAuditor`, which verifies claims against ground truth
rather than trusting self-reports. Two verification methods to implement:

1. `verify_files_modified(self, claimed_files: list[str], since_commit: str,
   repo_path: str | Path) -> dict` — runs `git diff --stat <since_commit> HEAD`
   (via `subprocess.run`, real git, not string matching against a log) in
   `repo_path`, parses the actual changed file list, and returns
   `{"claimed": claimed_files, "actually_changed": [...], "verified": bool,
   "discrepancy": [...]}` where `verified` is True only if every claimed file
   appears in the actual git diff, and `discrepancy` lists claimed files that
   did NOT actually change.

2. `verify_test_result(self, claimed_result: dict, test_command: list[str],
   cwd: str | Path) -> dict` — actually re-runs `test_command` via
   `subprocess.run` (e.g. `["python3", "-m", "pytest", "path/to/test.py", "-v"]`),
   captures real stdout/returncode, and returns
   `{"claimed": claimed_result, "actual_returncode": int,
   "actual_passed": bool, "verified": bool}` where `verified` compares
   `claimed_result.get("passed")` against the real observed pass/fail
   (returncode == 0).

Also implement `audit_historical_log(self, log_path: str | Path,
sample_size: int = 1000) -> dict`: reads the FIRST `sample_size` lines of the
real `.nexus_execution_log.jsonl` format (fields: `timestamp`, `directive`,
`directive_file`, `status`, `code_lines`, `coverage`, `audit_approved`,
`deployed` — confirmed field names from this session's earlier
investigation, do not guess), and for each entry checks: does `code_lines`
vary at all across entries sharing the same `directive` name, or is it a
hardcoded constant? Returns a summary dict:
`{"entries_analyzed": int, "unique_directives": int,
"directives_with_constant_code_lines": int,
"directives_with_variable_code_lines": int,
"verdict": "LIKELY_FABRICATED" | "LIKELY_REAL" | "MIXED",
"evidence": {...per-directive breakdown...}}`.
Verdict rule: if >= 90% of directives (with >= 5 samples each) show a
constant `code_lines` value, verdict is `LIKELY_FABRICATED`. This
function's job is to make the finding from this session's manual
investigation into a reusable, automated, reproducible check — the numbers
it produces on the real log should corroborate (not necessarily
exactly match, the manual check sampled differently) what was found
manually: a small number of directive names, each with an unvarying
code_lines value.

Write tests in
`systems/engineering_studio/studio_v3/tests/test_independent_auditor.py`:
- `verify_files_modified`: set up a temp git repo, commit a file, note the
  commit hash, modify+commit a second file, then call with a claim listing
  BOTH the actually-changed file and a fabricated non-existent filename;
  assert `verified == False` and the fabricated filename appears in
  `discrepancy`. Then call with a claim listing ONLY the real changed file;
  assert `verified == True`.
- `verify_test_result`: use a trivial real test file (write one to a temp
  dir with one passing `assert True` test), call with a claim of
  `{"passed": True}`; assert `verified == True`. Then write a failing test
  (`assert False`), call with the same claim `{"passed": True}`; assert
  `verified == False` (the claim was wrong).
- `audit_historical_log`: build a temp JSONL fixture with 20 lines: 15 lines
  across 3 directive names each with a CONSTANT code_lines per name (fabricated
  pattern), 5 lines for a 4th directive name with genuinely varying
  code_lines (real pattern) — assert the function correctly identifies which
  directives are constant vs variable, and that the mixed fixture yields
  verdict `"MIXED"`.
- Also run `audit_historical_log` against the REAL
  `${NEXUS_ROOT}/.nexus_execution_log.jsonl` with
  `sample_size=1000` as an integration-style test (mark it clearly, e.g.
  function name `test_audit_real_execution_log`) — do not assert a specific
  verdict value in a way that would break if the log format changes, but DO
  assert the function runs without error and returns a well-formed dict with
  `entries_analyzed == 1000`. Print (or log) the actual verdict — this is the
  evidence the Task 4 report will cite.
